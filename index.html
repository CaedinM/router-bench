Evaluation cookbook · Router Bench

Evaluating model routers for cost and accuracy

Compare three routing approaches on the same questions, vary their instructions, and measure the downstream quality, total cost, and routing latency of each configuration.

Caedin MNovember 3, 2026Run the notebook locally

Why evaluate model routing?

Applications often receive requests with different levels of difficulty. A short factual question and a multi-step coding task may arrive through the same interface, but they don't require the same model. Sending every request to a higher-cost model can spend more than necessary; sending every request to a cheaper model can reduce answer quality. A router attempts to make that choice for each request.

This makes routing relevant to mixed-traffic assistants, coding workflows, and systems with fixed inference budgets. The decision also introduces its own cost and latency. Savings on the selected model are useful only when considered alongside the quality of its answer and the overhead of choosing it.

We chose this topic to compare specialized decision models with a lightweight language model as routers. We want to understand three things: how their selections change downstream benchmark performance, how much the routing objective affects those selections, and how routing overhead changes the cost and latency comparison.

This cookbook walks through the routing experiment notebook. To run it locally, clone the repository and follow the setup instructions. The walkthrough covers dataset preparation through evaluation. We use Jev, OpenAI Decisions, and Claude Haiku 5.5 to choose among three anonymous solving models. The experiment is a research comparison: its results describe this candidate pool and these benchmark questions, rather than establishing a router for deployment.

What we will do

  1. Set up the notebook and Phoenix.
  2. Prepare paired benchmark records and fixed splits.
  3. Define the shared anonymous candidate contract.
  4. Choose routers and a routing objective.
  5. Run comparable routing experiments.
  6. Evaluate saved decisions without calling solvers.
  7. Summarize results with explicit weighting.
  8. Interpret the published results and takeaways.

02Prepare the benchmark dataset

Run the dataset preparation cell on first use, or when the required splits are missing:

upload_dataset()

The active source is data/intern_flash_gpt5/, imported from LLMRouterBench. Each question has published records for all three solving models, including scores and execution costs. We upload those records as private reference outputs and use the question text from the Gemini 2.5 Flash record as the shared routing input.

Engineering decision: replay published outcomes. Calling a selected solver after every routing decision would repeat solver inference for every experiment. Instead, we make live routing calls and look up the selected solver’s archived outcome afterward. This keeps the solving outcomes fixed while we compare routers and prompts. It also means the evaluation measures selection among existing outcomes, without testing fresh solver responses.

The dataset has a fixed 30-question development split, with three questions per benchmark, and a 12,416-question test split. Saved question identifiers preserve the original development membership. We use development for checking the workflow; there is no separate router training or calibration stage.

03Keep the routing contract consistent

A router should choose from the capabilities and prices provided in the experiment. Model names can introduce prior beliefs that are outdated or inconsistent across decision models, so every router receives the same three neutral labels and the same public-source descriptions.

The fixed mapping below is for readers and evaluation code. It is kept outside router-visible inputs in routing/candidates.py:

Private candidate mapping used throughout this benchmark.
LabelSolving model
Candidate AIntern-S1 (intern-s1)
Candidate BGemini 2.5 Flash (gemini-2.5-flash)
Candidate CGPT-5 Medium (gpt-5)

The active profiles in routing/prompts.py are:

Candidate A: General and scientific reasoning capabilities; $0.18 input / $0.54 output per million tokens.
Candidate B: General-purpose language, coding, and reasoning capabilities; $0.30 / $2.50.
Candidate C: Coding and complex reasoning at medium effort; $1.25 / $10.00.

These descriptions are grounded in the Intern-S1 model card, Gemini documentation, and GPT-5 documentation. We do not derive them from this project’s test results. The rates are historical inputs to the routing decision; downstream cost evaluation uses each original published execution cost.

Engineering decision: separate routing inputs from evaluation references. In a real-world system, the router would receive an incoming user prompt without additional labels identifying the type of task. We reproduce that setting by giving the router only the question prompt, shared instructions, and anonymous candidate profiles. It must infer the task and its difficulty from the request itself. Benchmark names, task categories, solver identities, archived responses, scores, and reference metadata stay outside the routing request; exposing them would give the router information it would not have when handling a real prompt. All approaches see the candidates in the same order. GPT-5 Medium serves as the top tier within this benchmark’s available pool.

04Choose routers and a system prompt

In the notebook’s Choose routers cell, select all three approaches or a subset:

selected_routers = ["jev", "openai-decisions", "haiku"] # Update this list to test a subset of models

router_settings = {
    "jev": {"provider": "jev", "model": "jev-1.13.0"},
    "openai-decisions": {"provider": "openai_decisions", "model": "gpt-6-luna"},
    "haiku": {"provider": "anthropic", "model": "claude-haiku-5-5", "parameters": {"max_tokens": 4096}},
}

Note: A shared interface adapts the same instructions and candidates to each provider’s request format and validates returned labels, reporting invalid decisions as failures rather than defaulting to a candidate.

We use different system prompts to evaluate how the routing models interpret and generalize across slightly different sets of routing instructions. By varying the emphasis on cost and accuracy while keeping the questions and candidate profiles fixed, we can observe how each model translates those instructions into candidate selections.

Next, select a system prompt variant:

system_prompt_variant = "default" # Set to "balanced", "accuracy-first", or "cost-first" to adjust behavior

custom_system_prompt = None  # Set to your own instruction string to override the default prompt.

The default asks the router to assess the request against the supplied capabilities and costs, then select the candidate that best fits. We replace that objective sentence for the other three variants, leaving the candidate descriptions and response contract unchanged:

  • Default: “Select the candidate that best fits the request.”
  • Balanced: “Balance cost and accuracy. Select the least expensive candidate that you expect to provide an accurate answer to the request.”
  • Accuracy-first: “Prioritize highest accuracy. Only downgrade to a cheaper candidate when you are confident it can accomplish the task.”
  • Cost-first: “Prioritize lowest cost. Only upgrade to a more expensive candidate when you do not believe a cheaper candidate can accomplish the task.”

This isolates the routing objective as an experimental variable. Three routers and four variants yield twelve configurations. A custom system prompt is supported, but leave custom_system_prompt = None when comparing the supplied variants.

Initialize the selected routers after choosing the prompt:

routers = []
routers = [
    build_router(
        name=name,
        system_prompt_variant=system_prompt_variant,
        custom_system_prompt=custom_system_prompt,
        **router_settings[name],
    )
    for name in selected_routers
]

Initialization makes no routing requests. Re-run this cell whenever router settings or instructions change so the next experiment uses the intended configuration.

05Run the routing experiments

Start with the notebook’s development settings:

split = "development"
benchmarks_filter = None  # None or a subset such as ["aime", "gpqa"].

Set benchmarks_filter to a list such as ["aime", "gpqa"] for a narrower check. Filters remain inside the chosen development or test partition. To evaluate the full test set, change split to "test" and keep benchmarks_filter = None.

Now run the experiment cell. This makes paid routing requests. No solving model is called.

results = await run_routing(routers=routers, split=split, benchmarks=benchmarks_filter)

Engineering decision: share one dataset version. The runner loads the selected dataset once and passes that same version to each selected router. It records the dataset version, candidate mapping, full system prompt, prompt hash, router configuration, and concurrency in experiment metadata. When comparing separate runs for different prompt variants, verify that their saved dataset version IDs match.

Routers run sequentially, with up to 16 concurrent questions within each experiment. This provides bounded throughput while keeping the concurrency setting consistent across approaches. Each run creates a new Phoenix experiment and a unique JSONL log in routing/results/; rerunning does not resume an earlier experiment.

For each of the four prompt variants, reinitialize the routers, run the selected split, and evaluate the returned experiments before moving to the next variant. The notebook’s results variable contains only the most recent run. Keep the printed experiment IDs and log paths for comparisons across variants.

06Evaluate saved decisions

Run the notebook’s evaluator cell after routing finishes:

from evaluators.all_metrics import evaluate_experiment
from routing.pipeline import make_phoenix_client

# Evaluate the experiments returned by the most recent routing run.
evaluation_results = {}
evaluation_client = make_phoenix_client({}, asynchronous=True)
try:
    for router_name, experiment in results.items():
        experiment_id = experiment["experiment_id"]
        print(f"Evaluating {router_name}: {experiment_id}")
        evaluation_results[router_name] = await evaluate_experiment(
            evaluation_client, experiment_id
        )
        print(evaluation_results[router_name])
finally:
    await evaluation_client._client.aclose()

The evaluator resolves each anonymous decision to its private model mapping and reads that model’s published record for the same question. No new solver inference or model-based grading is needed. It attaches these metrics to the saved experiment:

  • downstream_score and downstream_cost: the selected solver’s published score and original execution cost, with token counts recorded separately.
  • router_latency_seconds and router token metrics: measured routing time and recorded API usage.
  • routing_cost: an estimate from recorded routing usage and the evaluator’s fixed historical pricing snapshot.
  • total_system_cost: routing cost plus the selected solver’s published execution cost.
  • gap: the best published score among the three available candidates minus the selected candidate’s score. Zero includes ties.

Engineering decision: separate selection quality from measurement errors. Failed routing tasks are skipped by evaluators and reported. Missing or malformed metric inputs produce errors or missing values rather than invented zeros. Inspect task and evaluation errors before comparing summaries. Routing cost estimates cover recorded usage and may omit charges for failed or retried requests that did not report usage.

Open local Phoenix, navigate to Datasets and Experiments, and select the printed experiment IDs. Inspect individual choices alongside downstream scores, costs, and errors. This helps distinguish a genuine low-cost selection pattern from incomplete evaluation data.

07Summarize results

Run the notebook’s Experiment summary cell, followed by Results by benchmark split. The first produces an overall view of the most recent experiments; the second groups their saved metrics by benchmark.

The notebook and README use the same accuracy aggregation: compute the mean published downstream score within each benchmark, then average those benchmark means with equal weight. Each of the ten benchmarks contributes equally in a full run, so larger datasets such as SimpleQA cannot skew the overall score simply by having more questions. When selecting a subset, each selected benchmark receives equal weight.

Total cost per 1,000 prompts is the mean eligible per-question routing-plus-solver cost multiplied by 1,000.

The per-benchmark table’s Total Cost (USD) is a sum for that group, without scaling to 1,000 prompts.

Relative to always using GPT-5 Medium, that is about 41% lower cost with a 9.61 percentage-point lower score. Every tested routing configuration scores below that fixed GPT-5 baseline and costs less.

Against Intern-S1, routing is not uniformly an accuracy improvement. Decisions with the balanced prompt scores 44.90%, slightly below the 44.93% fixed baseline; its cost-first configuration matches the baseline score while adding routing overhead. Against the mid-tier baseline, several configurations score lower despite higher total cost. These references are essential when interpreting a router’s score in isolation.

Candidate selection patterns

Decisions selects Intern-S1 on 87.9% of questions under the default prompt and 100.0% under cost-first. Its accuracy-first prompt still selects Intern-S1 on 97.7%. This demonstrates a strong preference for the cheapest candidate in these experiments; it does not establish an inherent property of the API across other prompts or candidate pools.

Jev and Haiku change their selection mix more visibly. Jev’s equal-benchmark score rises from 46.94% with balanced prompting to 53.30% with accuracy-first prompting, while total cost rises from $6.27 to $15.94. Haiku’s accuracy-first configuration sends 24.3% of questions to GPT-5 Medium, the largest share among the tested configurations.

Routing latency

Jev has the lowest measured mean routing latency at 0.173 seconds, followed by Decisions at 0.312 seconds and Haiku at 1.911 seconds. These timings describe routing calls under the experiment’s concurrency conditions. They do not include solver latency or establish end-to-end application response times.

Takeaways

  • Tune your system prompt. Small changes to routing instructions can meaningfully change model selections, accuracy, and cost. Switching Jev from balanced to accuracy-first prompting increased its score by 6.36 percentage points while more than doubling total cost. Tuning the prompt is therefore an important part of aligning routing behavior with your cost and accuracy priorities.
  • Cheaper routing cost doesn't always lead to savings. OpenAI Decisions API had higher routing costs than Jev, but its stronger preference for cheaper solving models produced lower total inference costs across all four matched prompt configurations. The selected solver’s cost outweighed the savings from Jev’s cheaper routing calls.
  • Each router shows a distinct strength. An interesting pattern emerges across the three approaches: Haiku achieves the highest routed accuracy, Jev makes routing decisions fastest on average, and Decisions produces the lowest total costs. Each leads on a different dimension of this benchmark.

Limitations and interpretation

  • The real-world motivation is allocating inference effort across requests. This evaluation isolates one part of that problem: choosing among three candidates from question text and anonymous capability profiles. It does not measure live solver behavior, end-to-end agent completion, or production workload performance.
  • The candidate pool is limited to models with outcomes in the source dataset. A different pool, pricing schedule, or workload could change the ranking. Published scores and execution costs remain historical. Router costs use fixed pricing snapshots, and routing timings reflect the measured concurrency and service conditions.
  • Four prompt variants demonstrate sensitivity to instructions without establishing an optimal prompt. The reported point estimates do not establish statistical significance, and the development split is a small workflow check. Source-data anomalies, failed tasks, missing metrics, and aggregation choices must remain visible when interpreting a run.

Within those limits, the evaluation gives us a reproducible way to compare routing approaches: hold questions and candidate information constant, vary the router and its objective, then pair each saved decision with a published outcome. The results show how those choices change the cost–quality tradeoff in this benchmark.
